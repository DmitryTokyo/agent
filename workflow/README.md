# Как мы разрабатываем с агентом

Общий порядок работы во всех моих репозиториях: путь от фразы пользователя до слитого изменения и закрытой задачи.
Особенности репозитория записаны в его `AGENTS.md` и `docs/agents/*`. Если они расходятся с этим файлом, прав
репозиторий. Где лежит каждый вид знания, сказано в [`knowledge-map.md`](knowledge-map.md). Как начать работу в
новом репозитории, описано в [`START.md`](START.md).

Агент выполняет шаги скиллами из `~/dev/agent/agent-kit`, оглавление — `INDEX.md`. Имена в обратных кавычках
(`create-plan`, `code-review`) — это скиллы.

## Что решает репозиторий

Каждый репозиторий записывает у себя:

- **Режим.** «Прямо в `main`» подходит маленькой утилите: веток, PR и ревью нет, каждый тикет — коммит в `main`,
  незаконченная работа в `main` допустима. Остальные репозитории работают в режиме «ветки и PR», он по умолчанию.
  Только в нём действуют раздел «Ревью и PR» и запрет push в `main`.
- **Префикс задач.** Ключ задачи — префикс плюс номер задачи в трекере: `PC-12` — это задача #12. По ключу называют
  ветки и коммиты.
- **Язык** общения и задач. Код и коммиты пишем по-английски, если репозиторий не решил иначе.
- **Стек**: язык, менеджер пакетов, чем подгружается окружение.
- **Фича-флаги.** Нужны, если стек их поддерживает и с ними проще держать незаконченную работу в `main`.
- **Потолки размера** `AGENTS.md` и `docs/agents/*` (раздел «Память и сессии»).

## 1. Задачи

- Агент пишет задачу по фразе пользователя, пользователь утверждает. Агент может сам предложить черновик, но в работу
  он идёт только после ОК.
- В описании три раздела: Problem, Goal, Links. Границы, критерии и решения живут в `plan.md`. До планирования у
  задачи есть только цель, критерии пользователь утверждает вместе с планом.
- Описание правят на месте и оставляют комментарий: что поменяли и почему.
- История задачи в трекере — комментарии с копиями утверждённых версий `plan.md`: `plan.md vN` и строка
  `Changed: …`. Копия идёт только из файла в трекер, обратно её не читают. По ленте копий виден ход задачи, а рабочий
  документ остаётся один.
- Классификация — две группы меток: `Product Value` (Core / Supporting / Generic) и `Work Type` (Feature / Bug /
  Refactoring / Engineering / Infrastructure / Maintenance). `Engineering Risk` и маршрут (workflow 1 / 2 / 3)
  пишутся только в `plan.md`: риск растёт по ходу работы, и копия в трекере от него отстанет. Чем выше риск, тем
  глубже проверки.
- Задача без кода (документ, разбор журнала поправок) получает метку `Документ` и идёт по цепочке задач-документов
  из раздела 4. Классификации и маршрута у неё нет.
- Утверждённый план агент меняет только после ОК: показывает изменённые строки, поднимает Version, копирует новую
  версию в трекер.
- Если на планировании меняется суть задачи, агент заводит новую задачу, а старую закрывает со ссылкой на неё.

## 2. Нарезка

- Три уровня: эпик (родительская задача в трекере), задача (подзадача) и тикет (локальный файл, один коммит).
- Большую работу ведём эпиком: `research` → `brainstorm` → `create-design` → `to-tasks`. В описании эпика Problem,
  Goal, Links и сводка дизайна в 3–5 строк. Открытые вопросы закрываем в research и design, до нарезки.
- Roadmap два. Roadmap проекта — этапы и эпики — живёт только в трекере, файла у него нет. `roadmap.md` эпика — его
  план: задачи по порядку, Epic checks, условия остановки, контрольные точки. Рабочая копия лежит в
  `.ai/epics/<slug>/`, утверждённая версия — комментарием в родительской задаче. Статусы задач — только в трекере.
- Эпик режем вертикальными срезами: задача — это то, что актор сам заметит после слияния. Задачи связаны через
  «blocks». Первая задача эпика — самый тонкий путь через все слои. Пользователь утверждает `roadmap.md` целиком.
- Задачи режет агент, пользователь их утверждает. Тикеты агент режет сам.

## 3. Выполнение

- Цепочка: взять задачу → `create-plan` → `to-tickets` → `orchestrate` (один тикет — один коммит) → PR.
- План состоит из двух файлов. `plan.md` пишется для пользователя, умещается на экран, пользователь утверждает его до
  кода. `agent.md` пишется для агента и ссылается на `plan.md`. Человеку и агенту нужны разные тексты, общий плох
  для обоих.
- Решения по ходу работы зависят от веса:
  - мелкое решение внутри тикета, критерии не меняет → агент решает сам и пишет в `notes.md`; отклонения от плана
    перечисляет в описании PR;
  - решение меняет критерии или границы → агент останавливается и спрашивает; после ОК пишет новую версию `plan.md`
    и копирует её в трекер;
  - решение влияет на другие задачи или архитектуру → агент останавливается и предлагает ADR, ссылку на него ставит в
    новую версию плана.
- Папка `.ai/` лежит вне git. Где лежит папка задачи, такой у неё и статус в трекере:
  - папки нет — Backlog или Todo; папку создаёт `create-plan`, когда задачу берут в работу;
  - `.ai/tasks/` — In Progress, здесь одна задача; пользователь может править её файлы;
  - `.ai/waiting/` — Paused;
  - `.ai/done/` — Done, история;
  - `.ai/epics/<slug>/` — рабочие файлы эпика и ссылки на папки его начатых задач;
  - `.ai/inbox/` — заметки «запиши, чтобы не отвлекаться».
- Источник правды — трекер. Статус и папку агент меняет одним действием, больше их никто не переносит. На старте
  сессии агент сверяет папки с трекером и сообщает о расхождениях, а чинит их после ОК.
- В `done/` агент заглядывает только по просьбе пользователя. Сначала `done/index.md` — строка на задачу, потом
  `summary.md` задачи — до 15 строк: итог, ссылки, решения, ревью и число раундов, отложенное. Дальше одна нужная
  ссылка. Старые планы противоречат текущему коду, а полное чтение съедает лимит.
- Inbox — файл на заметку: `.ai/inbox/<дата>-<суть>.md`, до 5 строк. Если выходит больше, это уже черновик задачи.

  ```markdown
  # <что сделать или запомнить, одной фразой>

  - Создана: <дата>, во время <KEY-N> (<что делали>)
  - Суть: <условие → результат, понятно без разговора>
  - Зачем: <только если пользователь назвал>
  - Связано: <задача / документ / —>
  ```

  Если для «Сути» не хватает данных, агент сразу задаёт один вопрос. Заметки разбираем при закрытии задачи и по
  просьбе пользователя. Каждая становится черновиком задачи, записью в базу знаний или журнал поправок либо
  удаляется. Куда её деть, решает пользователь.

## 4. Ревью и PR

Раздел действует в режиме «ветки и PR».

- Каждая часть задачи проходит такую цепочку:
  1. Агент А пишет код. Локально он прогоняет только автоматические проверки тикета: `check`, тесты, `hygiene`.
     Потом коммитит, пушит и открывает PR скиллом `merge-request`. Если проверка красная, PR не открывается.
  2. Агент Б в другом харнессе запускает `code-review <KEY>-N <часть>`. Замечания он пишет в
     `.ai/tasks/<key>-N-<slug>/reviews/`, на каждый раунд новый файл.
  3. Агент А читает последний файл ревью и чинит. Следующий раунд снова проводит агент Б.
  4. Пользователь читает PR и оставляет комментарии с тегами.
  5. Пользователь проверяет результат руками по чеклисту, до слияния. В `main` попадает только проверенное.
  Между харнессами сообщения передаёт пользователь. Ревью агента лежит в файле, потому что его комментарии в PR
  выглядели бы как комментарии пользователя.
- Число раундов ревью агента показывает качество, в идеале раунд один. Число пишется в `summary.md` и в сводку
  разбора журнала поправок. Если раундов много, пользователь думает, не сменить ли модель, харнесс или правила.
- Тег — первое слово комментария пользователя в PR:
  - `issue:` → агент правит и пишет запись в журнал поправок;
  - `nitpick:` → если правка очевидна, правит и пишет в журнал; если нет, отвечает с доводом и ждёт;
  - `question:` → объясняет в треде, код не трогает;
  - `note:` → ничего не делает;
  - без тега → как `question`.
  Агент отвечает в каждом треде, закрывает треды пользователь.
- В PR пользователь смотрит на главное: слои и границы, модули, есть ли смысл в тестах, неожиданные зависимости,
  решения вне плана. Имена и стиль проверяют `hygiene-review` и агент на ревью.
- Размер. Тикет — до 100 строк продакшн-кода, один коммит. Часть — до 6 тикетов: одна ветка `<key>-N-<часть>` от
  свежего `main` и один PR. Если выходит больше, делим на две части и называем каждую по тому, что она даёт. PR на
  тысячи строк либо перечитывают, либо одобряют не глядя.
- PR закрывает задачу строкой `Closes #N`. Формат сообщения коммита проверяет хук `commit-msg`. При слиянии коммиты
  сохраняются (merge или rebase), squash не используем.
- У задачи из нескольких частей перед слиянием последней части проходит финальное ревью. Агент смотрит общий дифф от
  начала первой части до конца последней. Ищет дубли между частями, логику не в своём слое, забытые TODO и мёртвый
  код, несогласованные решения. Пользователю он готовит обзор. Серьёзные находки становятся тикетами на зачистку в
  последней части.
- Эпик закончен, когда пользователь сам прошёл все Epic checks в `roadmap.md`. Последний пункт — ревью агентом по
  слитому в `main` диффу эпика. Серьёзные находки становятся задачей на зачистку в том же эпике.
- Качество проверяется на четырёх уровнях: тикет (`check`, `hygiene-review`), часть (ревью агентом, ревью
  пользователем, проверка руками), задача (финальное ревью), эпик (Epic checks и ревью по слитому диффу).
- Stacked PR берём, только если ожидание ревью начнёт тормозить работу.
- Задача-документ. Агент задаёт вопросы по одному и сразу вписывает решения в черновик. Пользователь правит и
  утверждает текст, агент коммитит в ветку задачи и открывает PR, пользователь сливает. Плана и тикетов нет,
  `summary.md` есть. PR нужен, чтобы путь у всех задач был один.
- Принимает работу только пользователь: он сливает PR. После слияния по его команде агент запускает
  `close-merge-request` и за один проход обновляет `main`, переносит другие открытые ветки задачи на новый `main`
  (при конфликте останавливается и сообщает), закрывает задачу, пишет `summary.md` и отмечает задачу в `roadmap.md`
  эпика.
- Push. `--force-with-lease` разрешён только для веток задач. `--force`, `-f` и push в `main` запрещены настройками
  харнесса.

## 5. Знания и окружение

- Агент начинает с `AGENTS.md`, это источник правды для всех харнессов. `CLAUDE.md` только ссылается на него: Codex
  читает `AGENTS.md` сам, а Claude — нет.
- Карта знаний — [`knowledge-map.md`](knowledge-map.md). У каждого факта одно место, остальные на него ссылаются.
- Факты окружения записаны в `docs/agents/environment.md` репозитория. Формат описан в карте знаний.
- Машина: macOS, zsh. Переменные окружения подгружаются сами при входе в папку проекта, чем — решает стек.
- Время хранится и пишется в логи в UTC. Пользователь видит его в своём часовом поясе.
- Секреты. Файл `.env` лежит вне репозитория, в git — только путь к нему и `.env.example` с именами переменных.
  Настройки харнесса запрещают агенту читать этот путь и запускать `cat`, `printenv`, `env`. В `.env` только тестовые
  ключи. Вынести файл недостаточно: агент прочитает любой путь, если ему не запретить.

## 6. Исправление агента

- Журнал поправок — `docs/agents/corrections.md` в git. Агент сам и сразу пишет запись, когда пользователь исправляет
  его работу: `issue:` или `nitpick:` в PR, поправка в чате, проваленный по вине агента пункт проверки, заметка из
  inbox. В обычной работе агент журнал не читает.
- Формат записи:

  ```markdown
  - <дата> · <KEY-N> · <категория> · <источник: issue в PR | nitpick в PR | чат | ручная проверка | inbox>
    Было: <что сделал агент>
    Надо: <как правильно>
    Правило: есть, нарушено → <файл «раздел»> | нет
  ```

- Три записи одной категории с одной сутью — кандидат в правило. Агент отмечает это сразу.
- Раз в неделю агент разбирает журнал, это повторяющаяся задача-документ. Он сводит записи по категориям и для
  каждого кандидата предлагает исправление по лестнице усиления. Пользователь утверждает каждое. Правило относится
  либо к одному репозиторию, либо ко всем — тогда правится скилл или этот файл. Закрытые записи уходят в
  `corrections-archive.md` со ссылкой на коммит.
- Лестница усиления. Исправление ищем сверху вниз и спускаемся, только если верхняя ступень невозможна:
  1. Автоматическая проверка: линтер, pre-commit, тест.
  2. Обязательный шаг в скилле с проверяемым результатом.
  3. Текст скилла.
  4. Текст правила в `docs/agents/*`.
  Лестница действует везде, где агент предлагает новое правило. Текст агент может пропустить, проверку обойти не
  может.
- Сработало ли исправление, проверяем на трёх уровнях:
  1. Журнал: та же ошибка повторилась после нового правила — значит, правило не работает.
  2. Тест на автоматическую проверку: плохой пример из журнала становится фикстурой, проверка обязана его поймать.
  3. Eval-сценарий в `evals/<суть>/`, его прогоняют в чистой сессии при каждом изменении правила. Для текстовых
     правил и скиллов сценарий пишут после двух неудач, для правил `hygiene` — сразу.

## 7. Память и сессии

- Встроенная память харнесса выключена, в Claude Code это `autoMemoryEnabled: false`. Она лежит вне git и ревью,
  её видит только один харнесс, а записанный в неё обход молча ослабит проверки во всех следующих сессиях.
- Что нужно запомнить, агент записывает по карте знаний: поправку — в журнал, факт окружения — в `environment.md`,
  правило — по лестнице усиления, мимолётное — в inbox. Предпочтения в общении для всех репозиториев — в
  `~/.claude/CLAUDE.md`, для одного — строкой в его `AGENTS.md`.
- Обходить проверку агент не вправе: skip, xfail, отключённый хук, ослабленное утверждение. Он останавливается и
  спрашивает пользователя. Pre-commit падает на skip и xfail без ключа задачи в `reason`, `--no-verify` запрещён
  настройками харнесса.
- Pre-commit следит за потолками размера `AGENTS.md` и `docs/agents/*`, числа задаёт репозиторий. Если потолок
  превышен, агент предлагает, что объединить, что заменить проверкой, что удалить. Утверждает пользователь.
- Одна сессия — одна роль на одну часть: написать, провести ревью, починить по ревью. Каждое в новой сессии.
- На старте агент читает по порядку: `00-map.md`, текущий тикет или последний файл ревью, `agent.md` и то, на что
  они ссылаются.
- Состояние хранится только в файлах. Решение агент сразу пишет в `notes.md`, отметку в `00-map.md` ставит при
  коммите тикета. После сжатия контекста агент перечитывает те же файлы и ничего не теряет.
